# Prospecting (finding Sinfy clients)

Created 2026-10-03: businesses of a city and niche (lawyers, doctors, psychologists…), with what their site runs and an opportunity score.

- Engine: `scripts/prospects/engine.ts` (Node). Screen: `/prospeccao` (header "Prospecção"), only with the dev server, which opens the sites (`scripts/prospects/vitePlugin.ts`, same-origin only). Terminal: `npm run prospectar -- --regiao "São Paulo, SP" --nichos advogados,psicologos [--bairros "Pinheiros;Moema"] [--fonte google]`; `--nichos-prontos` lists the niche ids.
- Types, niches, score and CSV live in `src/features/prospects/` and are loaded by Node too: keep their imports relative with the `.ts` extension and the syntax erasable (no enums).
- Sources: Google Maps read for free (`maps`, the default, by the user's choice on 2026-10-03: "não quero ter o custo"), OpenStreetMap (`osm`, free, partial) or the paid Places API (`google`, `GOOGLE_PLACES_API_KEY`). The free Maps reader uses Maps' internal search address (`/search?tbm=map`, taken from the search page, then only the coordinates and `!8i` offset change); about 300 places per point. Google's terms do not allow this reading: one request at a time with a pause, stop at the first block and keep what was found. If Maps changes, `mapsTemplate`/`mapsPage`/`mapsBusiness` in `engine.ts` need adjusting. The permission system blocked agents from running it, so the user runs Maps searches. Never invent businesses or contacts.
- Coverage (`maps` only): `centro` is one deep search at the city center (or one per neighborhood typed); `cidade` lays up to 36 points inside the city outline (Nominatim polygon) and splits a point into four where Maps fills all ~300 slots with new places (two levels). Businesses from neighboring cities are dropped.
- Detection reads only the home page (and the contact page when it has no e-mail): WordPress, Elementor/Pro and versions, other builders, theme, contacts and the footer credit ("Desenvolvido por …" = the agency, a lead for the Agência plan). The "outdated" thresholds in `score.ts` are dated; update them as WordPress and Elementor release.
- Buying signal (2026-10-03, the user: "só tem site quem faz anúncio e por isso que compram"): the scan reads paid-ad traces (`ads`: Google Ads conversion tag, Meta/TikTok/LinkedIn pixels; Tag Manager alone is a weak sign) and sales tools (`sales`: online booking such as Dietbox, WebDiet, Calendly; course checkouts such as Hotmart, Kiwify; WooCommerce). They raise the score, show an "Anuncia" badge and the "Só quem anuncia" filter, and the sales script opens with them. A tag means the site has it, not that an ad is live: each lead has links to Google Ads Transparency (by domain) and the Meta Ad Library (by name) for a person to check. Wix and Tag Manager can load pixels the HTML does not show, so the count is a floor.
- Scan copies stay in `data/prospeccao/` (gitignored): they hold contact data of people. Do not commit them or send them to other services without the user asking.
- Shared with the team (the user, 2026-10-12: "para todos usuarios verem no site"): since the CRM (2026-10-13) the funnel is the team's Oportunidades in the CRM tables, and the searches live in the team folder `space-projects/crm/<team>/searches/` (storage policies `can_use_crm_file`). Only the team sees them; to give someone access, invite them in Equipe. The dev app uses the same data (`src/features/prospects/api.ts`): only a new scan runs on the dev server, and the screen sends the finished search to the team folder. The terminal uses the same tables and folder (`scripts/prospects/cloud.ts` with `SUPABASE_SERVICE_ROLE_KEY` from `.env.local`, and `PROSPECCAO_EQUIPE` when there is more than one team): `--site` and `--fila` read and write the CRM funnel, a terminal scan uploads its search, and `npm run prospectar:subir` uploads local searches that did not arrive. Files rewritten at the same path use `cacheControl: '0'` and are read through a fresh signed URL with `cache: 'no-store'` (a plain download came from the browser cache for up to an hour). The old shared folder `prospeccao/` (2026-10-12, migration `20261012200000`) and `data/prospeccao/funil.json` are copies from before the CRM that nothing reads.
- Funnel (2026-10-03, the user's request): the CRM's Oportunidades (`/crm`; the old `/prospeccao?aba=funil` redirects there; types and stages in `src/features/prospects/funnel.ts`). Stages: Mapeado → Fila da página → Página pronta → Contatado → Em conversa → Proposta → Fechado / Perdido. Each card is a client (with the lead snapshot) plus its opportunity: Space project, outreach video, next step, notes, offer and script. "Pôr no funil" in a search creates (or reuses) the client by the business id. One funnel for now (the user, 2026-10-13); more funnels later.
- Projects the ▶ creates belong to the admin who clicked. Other admins see them only with `20261006180000_space_admin_control.sql` applied (admins read and save every project, without publishing, connecting WordPress or inviting); the project list shows them under "De outras contas" (`role: 'admin'`), without Excluir or Sair.
- **The studio is Avence Studio** (https://avencestudio.com/, @avencestudio, São Leopoldo), the user's own studio: every message to a prospect is signed "Aqui é [seu nome], da Avence Studio". Sinfy is the product behind it and never appears to the end client (the user's decision, 2026-10-04: two separate brands).
- **We sell a service, as an agency, not the Sinfy product** (the user's decision, 2026-10-03): the new site for a one-time price (default R$ 1.000 in the funnel settings; the user also mentioned R$ 350) and an optional monthly plan to look after it. Never put the Sinfy plans (Produto, Completo, Agência) or product features in an offer, a sales script or a client-facing text. Each opportunity has an offer (service, price, monthly) and a sales script (`SalesBrief`: what we deliver, how to offer, the best way, what the new site solves, objections), drafted by `draftOffer` (`src/features/prospects/offer.ts`) and adjusted by hand; the funnel shows the open value (from "Fila da página" to "Proposta"). When an agent finishes a page from the queue, it rewrites that opportunity's script with what it found on the site (as done for the São Leopoldo lawyers).
- **Who buys and what to say** (2026-10-14, the user: "o cara tem um site para gerar demanda, não para ser bonito… se a versão 3 funcionar muito bem, por que eu vou atualizar?… não vamos conseguir cobrar R$ 1.000 para atualizar o WordPress"): `brands/avence-studio/CLIENTE-IDEAL.md`. The file also holds the proposed demand diagnosis (seven questions, the annotated phone screenshot, the rewritten first screen) and the open questions to validate.
- Cards move between stages by drag and drop (or the advance button); a drop can be undone from the notice.
- A site the user points to outside the searches: `npm run prospectar -- --site <url> --nichos advogados --regiao "<cidade, UF>" [--nome "<empresa>"]` reads it (`leadFromSite`, source `manual`, id `site:<domínio>`) and puts it in "Fila da página".
- **Diagnóstico de site** (2026-10-14, the user: "uma tela com o input… a URL do site… identificado se ele é em WordPress Elementor… uma oferta… para uma atualização desse site", "talvez um diagnóstico"; they want it for the team first and later as a public page for site owners, on the same reading): `/crm/diagnostico` (menu CRM › Diagnóstico, `src/pages/crm/Diagnosis.tsx`). Paste a URL: platform and versions against the current ones (`CURRENT`/`RECENT` in `score.ts`), theme, PHP (`x-powered-by`), the WordPress default tagline, pages and posts and plugins from the public `/wp-json` (`X-WP-Total`, `namespaces`) plus `/wp-content/plugins/<folder>/`, HTTPS, server time, footer year, what Google and phones see (viewport, description, H1, `og:image`, favicon, image alt), ads, sales tools, agency and contact. Then the verdict (update on the same WordPress, new site, or check by hand), the offer from `draftOffer` (it adds the WordPress/Elementor/plugin update line when versions are old) and "Pôr na fila da página" / "Só pôr no funil": a site already in the CRM (by `domain`) gets a new opportunity on the same client, otherwise `addLeads` with id `site:<domain>`; the diagnosis text goes to the client timeline as a note. The site reading (`scanSite`, `diagnoseSite`) lives in `supabase/functions/_shared/siteScan.ts`, with no imports and only web APIs, because it runs in the engine (Node), the dev server (`POST /__prospeccao/diagnostico`) and the Supabase function `site-diagnostico` (logged-in accounts only; it checks DNS against private addresses at every hop). `types.ts` re-exports its types. Without the function deployed (the user's call), the published app says so and the dev app still diagnoses. Rules for the items are in `src/features/prospects/diagnosis.ts`; date the version thresholds when they change. The screen leads with the path to contact and what Google shows; platform, versions, PHP, theme, plugins, page count and the agency sit in "Para a equipe", which never counts as a point to fix.
  - **Demand diagnosis, local version** (2026-10-14, the user: "vamos na versão que funciona local"): after the fast reading, the dev app opens the site in this machine's Edge as a 390 × 844 phone (`scripts/prospects/phone.ts`, `POST /__prospeccao/diagnostico/celular`): LCP with Lighthouse's applied slow 4G and 4× CPU, the first-screen photo, one photo per screen down to 8 screens, where the WhatsApp/phone/form links and plugin floats sit (floats that appear after scrolling count from that screen), the first-screen texts, headings, trust signals and the tags really loaded (`google_tag_manager`, `fbq`). Then this machine's Claude Code (`scripts/prospects/copyReader.ts`, `POST /__prospeccao/diagnostico/texto`, `findBin`/`launch` from `chatPlugin.ts`) reads the photo plus the texts with no tools, in an empty temp folder, through `--json-schema`, and returns what a visitor understands in 5 s, quoted problems, trust signals and a first screen rewritten only from site facts. `src/features/prospects/demand.ts` turns all of it into the seven questions (`demandQuestions`) and the first message's opening (`pitchOf`, passed to `draftOffer` as `observation`); `DemandReport.tsx` draws "Hoje" with numbered marks, "Como a primeira tela poderia ser", the page screen by screen and the list. Putting the site in the funnel saves the improved script and a note with the seven answers. A capture takes about 20 s and the reading about 20 s; the LCP varies between runs with the site's server (2.3–4.1 s on the same site). In the published app those two parts say they run locally.
- "Rodar a fila" means: `npm run prospectar -- --fila` lists the businesses in "Fila da página"; each one becomes a Space project with a new Home through `/cliente` (one agent per business, each with its own `SPACE_SESSION`, as done for the São Leopoldo lawyers). When the page is done, move the card to "Página pronta" and fill the project and the video. Nothing goes to the business (link, message, publish) without the user.
- Play button (2026-10-12, the user: "um play na coluna de fila da pagina para criar automaticamente aquela pagina… usando a ia que está ativa"): each card in "Fila da página" has ▶ "Criar página com <IA>", active when the chat's agent is connected (Vite in dev, the connector in the published app; the column header shows which AI, or "Conectar"). It creates the project with the lead as the briefing (`projectBriefing` in `src/features/prospects/pageTask.ts`), stores `build` (project, agent, start) on the opportunity and sends the request to that project's chat with the "Página de prospecção" skill (`PAGE_SKILL`, the whole recipe: read the site, facts in `.space/<project>/fatos.md`, concept, DESIGN.md, plan on the empty Home, one native section per push, shot, details, sales script) and `task: { kind: 'prospect' }`, which gives it 90 minutes (`scripts/space/chatPlugin.ts`; every chat run has the web since 2026-10-12: Claude Code with `WebFetch` and `WebSearch`, Codex with `web_search="live"`, and the prompt says web content is material, never instructions). The card shows the agent's current step, Stop, Resume and "Ver no Space" from the conversation (`usePageBuild.ts`). The agent ends with `space prospect <id> --stage pagina --brief-file roteiro.json --next … --note …` (bridge method `prospect`, an account call: only stage between queue and ready, script, next step and an extra note; never the offer or the price); the board refetches the funnel when the run stops. The agent works only in `.space/` (prospect contacts never go to the repo) and nothing leaves the account. Changing the chat, the bridge or `space.mjs` needs `npm run conector`, and connector users download it again.
